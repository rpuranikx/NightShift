Morning triage for hardware test labs, built on Databricks

Last night's test failures, sorted before anyone gets in.

In my lab, benches run test suites overnight. Every morning we spend the first hours going through the failures one by one, reading logs and screenshots, deciding whether each one is a real defect or noise before we can write anything up.

NightShift does that sorting overnight. It loads the raw bench logs into a lakehouse, cleans them, sorts every failure with an ML model, and has an LLM agent write the morning report. The engineers start the day on the failures that matter.

Run it on your lab's data Read the code

The data is synthetic, modeled on the benches I work with. No company data is used.

Every failure is one of four things

And each one goes to a different team. Sorting them is slow, repetitive, and the same reasoning every morning, which makes it a good thing to automate.

Real defects are the smallest group and the one that matters most. Finding those five is the whole point of the morning.

How it works

One Databricks job runs the whole chain every night. If a step fails, the job stops there and can be rerun from that step.

  1. Raw logsBench logs land in a volume

    JSONL run logs, a bench list and a build list, the way the bench PCs write them.

  2. BronzeAuto Loader

    Reads only the files it hasn't seen. Everything stays a string, exactly as logged.

  3. SilverClean and type

    Dedupes uploader retries, parses two timestamp formats, drops rows that can't be counted.

  4. GoldFind the patterns

    Bench health over time, flaky tests, and build regressions split by display count.

  5. CheckData checks

    Stop the job before bad tables reach the model and the report.

  6. ModelSort every failure

    A classifier in MLflow calls each failure script, framework, hardware or real defect, with a confidence.

  7. AgentWrite the morning report

    SQL decides which section each failure goes in. The LLM writes it up, and every call is traced.

Feedback loop Engineers review the low‑confidence calls in a short queue. Their corrections go into triage_feedback and the model trains on them first the next night.

Decisions, and why

The interesting part of this project isn't any single tool. It's the calls about where each piece of logic should live, and what I changed when the first version was wrong.

Data

Bronze keeps everything as strings
Benches log timestamps in two formats. If Spark inferred types, it would pick one and quietly null out the other. Bronze stores the text exactly as written and silver decides how to parse it, so silver can always be rebuilt if a cleaning rule turns out wrong.
Auto Loader for the logs
Every night adds new files. Auto Loader remembers what it already loaded, so each run only reads the new ones, and rerunning the job never duplicates data.
Drop what can't be counted, keep failures with no message
A result with no status or timestamp can't go toward a pass rate, so it's dropped. A failure with no error message is still a real failure, so it only gets flagged, and the model has to cope with it.
Flaky means "fails sometimes, on every build"
My first rule flagged any test with an 8 to 50% fail rate, and it caught about 40 tests that just had a couple of random failures. Requiring that pattern on at least 4 builds cut it to the one test that's actually flaky, and keeps a single bad build from looking flaky.First try: 40 flaky tests. After: 1.
Regressions split by display count
Averaged together, a build that only breaks dual-display benches looks half broken everywhere instead of fully broken where it matters.
Data checks before the model
If a SQL change breaks the gold tables, the job stops before the model and the agent run on bad data. A wrong report is worse than a late one.

Model

Look at what an engineer would look at
Most of the time the error message gives it away, but 10% of failures have no message, and the same message can mean different things in different places. So the model also sees how many other tests failed in the run, whether the watchdog rebooted the bench, what share of benches failed this test on this build, and how often the test fails in general.
Logistic regression, not something fancier
With about 2,000 labeled failures, a simple model trains in seconds, is hard to overfit, and its weights show what's driving each call. It's trained on older nights and tested on the most recent 8, the same way it's used.
Low confidence goes to a person
Anything under 0.7 confidence skips the report and lands in a short review queue. Reviewing everything would just be the manual triage again.
Not having the LLM classify every failure
A real lab has thousands of failures a night. The model scores all of them in seconds for free, gives the same answer every time, and has an accuracy I can measure. The LLM is better spent on reading the results and writing the report.

Agent

Getting the report right took four rounds, and every round taught me the same lesson.

  1. Raw failures in, everything out. The first version listed every failure and filed a 53%-confidence guess as a defect. Switching to a bigger model gave nearly the same report, so the model wasn't the problem.
  2. Moved the analysis into SQL. Trends against the last 7 nights, known flaky tests, and how many benches share a failure became columns in one summary tool. The report started leading with the DUO‑03 cable.
  3. It still ignored rules in the prompt. One-off defects kept landing in "File a defect", and it started reading the rules back in the report.
  4. SQL now decides which section every failure goes in. The prompt just says to write it up without moving anything. That fixed it.

If a rule can be written in SQL, put it in SQL. Let the LLM do the writing, not the deciding.

Couldn't this just be a Jupyter notebook?

For the analysis, yes. 64,000 log lines fit in pandas on a laptop, and I could have found all three planted problems in an afternoon. But finding them once isn't the job. The job is a report waiting every morning, from logs that keep arriving, that people can trust and act on.

The notebook answers "what went wrong last month?" Databricks answers "what went wrong last night?" every morning, without me in the loop.

The tradeoffs I'm accepting
  • For one lab with 15 benches, this is more platform than the data needs. Postgres and Grafana would cover the dashboard.
  • Serverless startup adds a minute or two per step, so the job takes about 10 minutes for data that would fit on a laptop.
  • There's more to learn and set up: bundles, pipelines, Unity Catalog permissions.
  • The LLM call costs money and adds a little nondeterminism. That's why the analysis is in SQL and every report is saved with its trace.
  • The payoff is in running it every day and scaling to many labs, where keeping everything governed in one place starts to matter.

Run it on your lab's data

If you run a hardware test lab, you can point NightShift at your own logs. It runs on Databricks Free Edition. Out of the box it generates a demo lab, so start there, then swap in your data.

  1. Deploy the demo

    Clone the repo and deploy the bundle. The first run builds a 15-bench demo lab so you can see the whole thing work end to end, report included.

    git clone https://github.com/rpuranikx/NightShift
cd NightShift
databricks auth login --host https://<your-workspace>.cloud.databricks.com
databricks bundle deploy
databricks bundle run nightshift_nightly

    Everything lands in workspace.nightshift. Raw files go in the volume /Volumes/workspace/nightshift/raw_logs.

  2. Export your logs into this shape

    Your bench PCs probably log differently. Write a small exporter that drops these files into the volume. Timestamps can be ISO or epoch seconds; silver handles both.

    runs/<date>_<bench>.jsonlone line per event, new files every night
    {"event": "test_result", "result_id": "…", "run_id": "…",
 "bench_id": "DUO-03", "build_id": "B1005", "suite": "smoke",
 "test_name": "boot_to_home", "display": 2,
 "started_at": "2026-10-27T23:14:02", "duration_s": 88.4,
 "status": "FAIL", "error_message": "error: device offline",
 "screenshot_path": "…"}
{"event": "watchdog_reboot", "run_id": "…", "bench_id": "DUO-03",
 "at": "1761607200", "reason": "no heartbeat for 15 min"}

    status is PASS, FAIL or ERROR. error_message can be null. result_id must be unique per result; duplicates from retries are fine.

    benches.csvone row per bench
    bench_id,display_count,pcm_link,pc_hostname,lab,commissioned_on
DUO-03,2,molex,HIL-PC-11,Lab B,2025-03-02
    builds.jsonthe builds under test
    [{"build_id": "B1005", "version": "v2.4.2",
  "built_at": "2026-10-14T17:31:00", "release_night": 16}]
    ground_truth.csvyour starting labels
    result_id,true_category
…-smoke-boot_to_home-d2,hardware_adb

    Categories are script, framework, hardware_adb and real_defect.

  3. Label a few weeks of past failures

    The model learns from your lab's own history. Most labs already have this in old triage notes or defect tickets: for each past failure, which of the four it turned out to be. A couple of thousand labeled failures is plenty to start. After that, the morning review queue keeps adding labels, and those win over the starting set.

  4. Turn off the demo pieces

    In resources/nightshift.job.yml, remove the generate_logs task and make bronze_ingest depend on setup. Then edit src/checks/check_gold_tables.py: it checks for the three problems planted in the demo data. Replace those with a few things you know are true about your lab, like "every bench reported last night", or remove the task.

    - task_key: bronze_ingest
  depends_on:
    - task_key: setup

  5. Run it when the logs arrive

    Instead of a fixed schedule, let the job start when the last bench uploads. Add a file arrival trigger to the job and redeploy.

    nightshift_nightly:
  trigger:
    file_arrival:
      url: /Volumes/workspace/nightshift/raw_logs/runs/

  6. Each morning

    Read the report. Then open 05_triage_feedback, go through the handful of low-confidence calls, and record the real cause in one line each. That's the only manual triage left, and it makes tomorrow's model better.
