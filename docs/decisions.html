What I chose, and why

Where each rule lives, and what I changed when it broke.

Data Model Agent Why Databricks

Data

Bronze keeps everything as strings
Benches log timestamps in two formats. If Spark guessed the types, it would pick one and quietly null the other. Bronze stores the text as written, so silver can always be rebuilt.
Auto Loader for the logs
New files land every night. Auto Loader remembers what it already read, so a rerun never duplicates data.
Keep failures with no message
A row with no status or timestamp can’t count toward a pass rate, so it’s dropped. A failure with no message is still a failure, so it’s only flagged.
Flaky means it fails on every build
My first rule flagged any test failing 8 to 50% of the time, and caught about 40 tests with a couple of random failures. Requiring that on 4 or more builds cut it to the one that’s really flaky.
Regressions split by display count
A build that only breaks dual-display benches looks half broken everywhere when you average it. Split, it’s fully broken where it matters.
Checks before the model
If a SQL change breaks the gold tables, the job stops before the model and the agent see them. A late report beats a wrong one.

Model

Look at what an engineer looks at
The error message usually gives it away, but 10% of failures have none. So the model also sees how many other tests failed in the run, whether the bench rebooted, how many benches failed this test on this build, and how often the test fails in general.
Logistic regression
About 2,000 labeled failures. A simple model trains in seconds, is hard to overfit, and its weights show what drove each call. It trains on older nights and tests on the latest 8, the way it’s used.
The LLM doesn’t classify
A real lab has thousands of failures a night. The model scores them all in seconds for free, the same way every time, with an accuracy I can measure.

Agent

Getting the report right took four rounds. Every round taught the same thing.

  1. Raw failures in. It listed every failure and filed a 53%-confidence guess as a defect. A bigger model wrote nearly the same report, so the model wasn’t the problem.
  2. Analysis moved into SQL. Trends, known flaky tests and how many benches share a failure became columns. The report started leading with the DUO‑03 cable.
  3. It still ignored prompt rules. One-off defects kept landing in “File a defect”, and it read the rules back in the report.
  4. SQL picks every section. The prompt just says write it up and don’t move anything. That fixed it.

If a rule can be written in SQL, it goes in SQL. The LLM writes. It doesn’t decide.

Why Databricks

Couldn’t this be a Jupyter notebook? For finding the problems once, yes. 64,000 log lines fit in pandas. The job is a report every morning that people can trust.

What it costs

  • For 15 benches it’s more platform than the data needs. Postgres and Grafana would cover a dashboard.
  • Serverless startup makes the job about 10 minutes for data that fits on a laptop.
  • The LLM call costs money and adds some randomness, which is why the deciding happens in SQL.
  • It pays off when it runs every day and grows to more labs, with one place for the data, the model and the permissions.
